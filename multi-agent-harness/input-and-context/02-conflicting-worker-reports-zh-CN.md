# 两位 Worker 得到不同结果，接手的人该相信哪一份？

[English](./02-conflicting-worker-reports.md) | [繁體中文](./02-conflicting-worker-reports-zh-TW.md) | [简体中文](./02-conflicting-worker-reports-zh-CN.md)

Worker A 在共享笔记里写下“版本 B 的台湾地址测试通过”。随后，Worker B 回信说“同一版本在导入订单时仍会拒绝台湾地址”，还附上了失败记录。接手写报告的 Worker C 如果只采用较晚的回信，就会漏掉已经验证的修复。如果照抄共享笔记，用户又会以为订单导入也通过了测试。

沿用前一篇的地址案例，假设原 Task 的验收条件是“地址验证函数能接受原先被拒绝的那条台湾地址”，门牌号是 `12號`。C 查看 A 笔记里的链接和 B 回信中的附件，确认两人测试的是同一个 revision。接下来要核对的是，两人分别从哪个入口提交了哪条地址，又在哪一步看到了结果。

| 测试输入 | A 的记录 | B 的记录 | C 可以写进报告的结论 |
|---|---|---|---|
| 普通门牌号 `12號` | A1 直接调用地址验证函数，函数接受了这条地址。 | B1 通过订单导入提交同一条地址，导入界面提示地址无效。 | 版本 B 的函数接受这条输入，订单导入仍会拒绝它。两项观察都应保留，导入失败的原因待查。 |
| 含连字符的门牌号 `12-1號` | A2 通过订单导入成功创建了测试订单。 | B2 使用同一份导入文件，系统提示地址无效。 | 两次测试都走订单导入。记录中的 revision、输入文件和地区设置也相同，结果为何不同仍待核实。 |

A1 直接回答了原 Task 的验收问题，C 可以把这份记录交给协调者，并在报告中单独列出 B1。B1 记录的是导入界面提示“地址无效”。仅凭这条提示，C 还无法判断哪一步拒绝了地址。接手调查的人可以从 B1 的导入文件查起，核对导入流程实际传给验证函数的值。如果要修改导入模块，还需另行确认任务范围。[另一位 Worker 的回信能改变我的任务吗？（繁体中文）](./01-peer-replies-and-task-scope-zh-TW.md)

## 哪个用例值得重测？

A2 和 B2 都经过订单导入，值得重测的是 `12-1號` 这个用例。如果 B 在回信里只写了“同一份文件”，附件却只有错误截图，C 应先请 B 提供当时使用的文件，或提供文件哈希值以便比对。拿到之前，可以先在笔记中写下“B2 报告导入遭拒，输入文件待核对”。仅凭门牌号相同，还无法确认整条输入一致。

在表中的案例里，C 已经比对过两份导入文件，可以请协调者安排验证者重测这个用例。验证者在干净的测试工作区检出版本 B，用留存的导入文件和原记录中的地区设置执行导入，记下本次实际加载的设置、导入返回的信息，以及是否创建了订单。如果再次遭拒，就有了一份可供追查的复现记录。如果成功创建了订单，也应记下这次成功，B2 当时为何遭拒仍待查明。

## 共享笔记该给下一位 Worker 留下什么？

在重测结果出来之前，C 就能把共享笔记中“台湾地址测试通过”这句话写得更准确。本例中的 A1、B1、A2、B2 分别指向各次测试的原始记录。

> 版本 B，台湾地址。原 Task 指定的 `12號` 函数测试已通过（A1）。同一条地址在订单导入时遭拒（B1）。另有一组 `12-1號` 的导入记录：A2 创建了订单，B2 提示地址无效。两次使用同一份导入文件，结果有出入，待验证者重测。

假设验证者报告这次成功创建了订单，C 可以在 A2、B2 旁补上一句：“在版本 B 上用同一份文件重测，成功创建了订单。运行设置和结果见重测记录 R1。B2 遭拒的原因待查。”下一位 Worker 调查那次失败时，仍然能找到 B2 的原始响应。协调者验收地址函数时，也知道该查看 A1。

如果实现者后来交付版本 C，这段笔记仍能作为版本 B 的对照。接手者可以沿用输入文件和测试步骤，单独记录版本 C 的结果，让协调者看清本次交付实际验证了哪些用例。[要求变了，哪些委派仍然有效？](../foundations/04-revising-delegated-work-zh-CN.md)
